# Interface languages (English / Arabic)

The interface ships in English and Arabic. Arabic is right-to-left and the whole
document switches with it.

## How the language is chosen

There is **no locale in the URL**. The application is a signed-in business
platform (every page is dynamic), so the language is resolved per request instead
of restructuring every route under `app/[locale]/...`:

| Priority | Source | Notes |
| --- | --- | --- |
| 1 | `Account.preferredLanguage` | The documented preference; `PUT /api/account/preferences` already writes it. |
| 2 | `clothing-locale` cookie | Covers signed-out pages; set by the switcher with a one-year lifetime. |
| 3 | `Accept-Language` header | First entry the application speaks (`ar-SA,ar;q=0.9` -> `ar`). |
| 4 | Default | `en`. |

`pickLocale` in `src/lib/i18n/index.ts` is pure, so the precedence is unit tested
without a request; `getInterfaceLanguage()` in `src/lib/i18n/server.ts` is the
server entry point (locale, direction, strings).

## Files

| Path | Role |
| --- | --- |
| `src/lib/i18n/index.ts` | Locale type, normalization, direction, precedence. |
| `src/lib/i18n/server.ts` | `getLocale` / `getInterfaceLanguage` for server components. |
| `src/lib/i18n/actions.ts` | `setLocaleAction`: writes the cookie and the account preference. |
| `src/lib/i18n/dictionaries/en.ts` | The English strings; the source of truth for keys. |
| `src/lib/i18n/dictionaries/ar.ts` | Arabic, typed as `Dictionary`, so a missing key is a build error. |
| `components/app-shell/locale-switcher.tsx` | One-click switch, used in the shell and on the login screen. |

`app/layout.tsx` renders `<html lang dir>`, and `app/globals.css` adds an
Arabic-capable font stack for `html[lang="ar"]` (the Latin UI fonts carry no
Arabic glyphs).

## Adding a string

1. Add the key to `dictionaries/en.ts`.
2. `dictionaries/ar.ts` now fails to compile until Arabic is added - that is the
   parity guarantee. `tests/unit/i18n.test.ts` additionally compares key paths and
   rejects empty translations.
3. Server components read `getInterfaceLanguage()`; client components receive the
   labels they need as props (the shell receives `{ nav, shell }` only, so the
   payload stays small).

## Writing direction

Use Tailwind's logical utilities so one class serves both directions: `ms-*`,
`me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`, `text-end`,
`border-s`, `border-e`. Physical `left/right` classes are what break RTL.

## Status

Done: the application shell (sidebar, header, page titles, sign-out), the login
screen, and the switcher.

Pending (per area, each one converts its strings and its direction-sensitive
classes): dashboard, catalog (products), cart/checkout, orders, deliveries,
payments, inventory, POS, customers, employees, roles, admin, reports,
notifications, account.

Also pending by design:

- **Server messages.** Validation and conflict messages come from the services in
  English. The stable `error.code` values are the hook for translating them later.
- **Business data.** Product names, category names and similar rows are entered by
  the business and stay exactly as stored; they are not translated.
